Архитектура и проектные решения приложения «Сканер конспекта».

## 1. Архитектурный подход

**Решение:** Одностраничное приложение (SPA) / Single-Activity App с навигацией по стеку экранов.
**Почему:** Приложение имеет линейный пользовательский путь (Главный → Скан → Набор → Повторение). Нет необходимости в сложной многооконности. Стек экранов позволяет легко реализовать требование «Кнопка "Назад" сбрасывает повторение» — достаточно просто `pop` из стека.

## 2. Технологический стек (Референсный)

- **UI:** Flutter (или React Native / Kotlin Multiplatform). Выбор обусловлен необходимостью иметь единый код для iOS/Android и легкий доступ к нативным камерам.
- **OCR:** ML Kit Text Recognition v2 (On-device).
  - _Почему:_ Спецификация жестко требует работу без интернета на русском и английском языках. ML Kit работает локально, бесплатен и не требует поднятия сервера.
- **База данных:** SQLite (через обертку типа `sqflite` или `Room`).
  - _Почему:_ Данные реляционные (Набор -> Карточки). Нужна гарантия сохранения между запусками. `SharedPreferences` / `UserDefaults` не подходят для хранения массивов объектов с вложенностью.
- **State Management:** BLoC / Redux / ViewModel.
  - _Почему:_ Требование «строка "Найдено карточек: N" пересчитывается при каждом изменении текста» означает реактивное состояние. Любое изменение в текстовом поле должно триггерить парсер и обновлять UI.

## 3. Структура Базы Данных

Спецификация говорит: «Сами фото и результаты повторений не сохраняются». Поэтому БД максимально плоская.

```sql
-- Таблица наборов
CREATE TABLE decks (
    id TEXT PRIMARY KEY, -- UUID
    title TEXT NOT NULL, -- "Конспект 08.10 14:32"
    created_at INTEGER NOT NULL -- timestamp для сортировки "новые сверху"
);

-- Таблица карточек
CREATE TABLE cards (
    id TEXT PRIMARY KEY, -- UUID
    deck_id TEXT NOT NULL, -- FK to decks.id
    front TEXT NOT NULL, -- Лицевая сторона
    back TEXT NOT NULL, -- Обратная сторона
    sort_order INTEGER NOT NULL, -- Порядок строк на фото
    FOREIGN KEY(deck_id) REFERENCES decks(id) ON DELETE CASCADE
);
```

**Почему ON DELETE CASCADE:** Спецификация требует удалять набор «без дополнительного подтверждения». Каскадное удаление избавляет от ручного перебора карточек в коде.

## 4. Модуль парсинга (Core Logic)

Это самый критичный модуль. Вынесен в чистую функцию `parseTextToCards(String rawText) -> List<Card>`.

**Алгоритм работы:**

1. Разбиваем текст по `\n`.
2. Для каждой строки применяем регулярное выражение поиска самого левого разделителя.
3. Регулярка: `(?:\s[-]\s|—|–|:|=)`
   - _Нюанс реализации:_ Стандартный поиск regex найдет первое совпадение слева направо, что идеально удовлетворяет требованию «самого левого разделителя».
   - _Дефис:_ Ищем строго `-` (пробел-дефис-пробел), чтобы отсеять «кто-то».
4. Если матч найден, сплитим строку на две части по индексу матча.
5. Делаем `.trim()` обеим частям.
6. Если `front.isEmpty` или `back.isEmpty` — скипаем строку (требование «пустой стороной не становится»).
7. Возвращаем массив валидных карточек.

**Почему функция чистая:** Это позволяет покрыть её Unit-тестами на 100% без запуска UI, проверяя все примеры из спецификации (`E = mc²`, `Время: 10:30`, `кто-то пришёл`).

## 5. Машина состояний экрана «Повторение»

Экран повторения реализован как очередь (Queue).

- **Инициализация:** Берем список карточек набора, перемешиваем (требование «в случайном порядке»). Создаем копию списка `queue`. Создаем словарь `firstTrySuccess = {cardId: true}`.
- **Показ:** Берем `queue[0]`. Рисуем лицевую сторону.
- **Тап (переворот):** Меняем флаг `isFlipped = true`. Показываем обратную сторону + кнопки «Знаю»/«Не знаю».
- **«Знаю»:** Удаляем элемент из `queue`. Уменьшаем счетчик `K`. Переходим к следующему `queue[0]`.
- **«Не знаю»:** Удаляем элемент из начала `queue`, добавляем его в конец `queue`. `firstTrySuccess[cardId] = false`. Счетчик `K` НЕ меняется. Сбрасываем `isFlipped = false`.
- **Завершение:** Когда `queue.isEmpty()`, вычисляем `X` (count where `firstTrySuccess == true`) и `Y` (общее число карточек в наборе). Открываем экран итогов.
- **Прерывание (Назад):** При вызове системного "Назад" мы просто уничтожаем стейт машины состояний. При следующем входе она инициализируется заново (требование «повторение сбрасывается»).

## 6. Обработка краевых случаев OCR

**Проблема:** Спецификация допускает ошибку в отдельной букве («Ошибка распознавания... не провал критерия»).
**Решение:** Мы никак не пытаемся исправлять опечатки OCR. Текст отдается пользователю «как есть» в редактируемое поле. Ответственность за корректность определений лежит на пользователе до нажатия кнопки «Создать карточки». После создания — изменить нельзя (согласно «Что НЕ делаем»).

## 7. UI/UX Детали

- **Склонение:** Реализовано через утилиту плюрализации на уровне View-слоя.
- **Превью фото:** Хранится в оперативной памяти (или временном кеше) только пока открыт экран «Распознанный текст». При уходе — уничтожается.
- **Swipe-to-delete:** Используется стандартный паттерн `Dismissible` (Flutter) или `ItemTouchHelper` (Android). Свайп влево сразу вызывает `DELETE FROM decks WHERE id = ?`. Никаких диалогов «Вы уверены?».
